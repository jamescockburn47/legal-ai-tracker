# Security and recovery — 22 October 2026

## Application controls
- Sites supplies identity. Forged identity headers were stripped in a live origin test: profile remained anonymous and workspace returned 401. Custom-domain requests from the development environment return 403; this is an unresolved verification limit, not a finding that the public website is unavailable.
- Owner authorization requires both platform identity ID and the configured owner email. Updater credentials can stage proposals, never approve. No public paid-AI endpoint.
- Shared D1 request budgets per minute: analytics 3,000; mail 300; other writes 600; uncached reads 3,000. Authenticated operator requests use a separate 120/minute budget so public budget exhaustion does not consume the editorial budget. Signed-in non-mail writes also have 60/user/minute. Browser identifiers, query strings and caller-supplied forwarding headers cannot select these budgets. Shared budgets are an emergency brake, not a substitute for platform DDoS mitigation; a distributed attacker can deliberately exhaust them. Denied budgets are cached per isolate until the next window to reduce database pressure.
- Only records/topics/overview GET responses are cached for 30 seconds, with canonical query ordering. No account, approval, backup or subscriber response enters that cache. An approved update can therefore take 30 seconds to appear in a cached response.
- Worker bounds request bodies before route parsing: 500 KB ingestion, 100 KB other APIs. Routes retain their narrower checks. Streaming bodies are bounded even without Content-Length.
- CSP restricts origins, objects, forms and framing; permissions policy disables unused camera/microphone/location/payment. Framework inline scripts/styles currently require unsafe-inline. This is partial CSP hardening, not a nonce-based XSS defence. ChatGPT framing remains allowed. HTTPS transport and MIME protections applied in Worker.
- No public arbitrary-email signup is enabled. Existing signed-in opt-in still uses confirmation, expiry, throttling and signed delivery webhooks. Delivery remains disabled pending live tests.

## Backups and recovery
- First uncached API request triggers a UTC daily transactional snapshot to a private R2 binding. No traffic means no new snapshot. Checks are throttled in each Worker isolate; a database lease prevents overlapping snapshots.
- Application tables include private notes, subscriptions and delivery tokens: treat backup files as sensitive. No backup objects are public. Owner GET /api/security lists available snapshots; append ?download=backups/YYYY-MM-DD.json to download one while signed in. POST /api/security with a same-origin request attempts today's snapshot. An existing daily snapshot is not overwritten.
- Snapshots older than 30 days are removed during successful backup maintenance. Expiry cleanup is traffic-dependent. The backup is in the same platform account: it does not protect against total account loss or malicious platform administration. Keep a separately secured offline copy for that risk.
- Restore rehearsal: `node scripts/restore-backup.mjs backup.json NEW-database.sqlite`. Destination must not exist. Applies repository schema, replaces migration seed rows with snapshot data, restores in a transaction, checks SQLite integrity. Never writes production. Recovery into production is a deliberate operator action using supported database import tooling; the site has no remote restore endpoint.
- Local recovery tests passed with test data. Production snapshot creation still requires verification after deployment. Export has a 20 MB safety ceiling; larger datasets need a streaming backup design. Do not treat this as an unlimited-scale backup system.

## Monitoring and operator actions
- Inspect owner /api/security for snapshots, and Sites Worker logs for security:backup_failed / security:limiter_unavailable. No email or external incident notifications have been configured.
- Enable MFA/passkeys on the owner ChatGPT, domain registrar and email-provider accounts. This cannot be established by application code.
- Use provider traffic controls if volume rises beyond the shared budgets; review measured legitimate traffic before raising limits. These are not measured capacity guarantees or load-test results.
- Dependency versions are pinned by the lockfile. A production dependency registry audit identified advisories; affected packages were updated to the reported patched versions. Final pnpm production dependency audit on 22 October 2026 reported zero known advisories (250 dependencies including optional dependencies). This is not proof that the software has no vulnerabilities. An automatic dependency update service remains to be configured.
- Never place keys in source or browser code. Existing updater credential is retained so scheduled editorial proposals continue working; splitting it from platform service access needs coordinated credential delivery to the automation.
